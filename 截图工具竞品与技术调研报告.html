零、结论先行（TL;DR）

  1. 市场不缺截图工具，缺的是"两端都一流 + 真正轻量"的那一款。 Mac 侧是 CleanShot X / Shottr 的天下，Windows 侧是 ShareX / Snipaste / PixPin 的天下，同一人在两台机器上用同一款工具、得到一致体验——目前基本无解。
  2. "轻量"是真实且被低估的护城河。 Shottr 2.3MB、Greenshot 4MB、ShareX 6.6MB 的口碑，直接对照 PixPin（Mac 版近 100MB、内存泄漏投诉）和 Kap（Electron 200–400MB）。社区对"常驻工具吃内存"的容忍度极低。
  3. 长截图是全行业最不稳的功能。 几乎每一款工具的评论区都在吐槽拼接错位 / 挑 App，同时它又是国内用户（被 QQ、微信训练过）的硬性期望。做得稳 = 直接建立差异化。
  4. Windows 端的第三方缺口远大于 macOS。 Win11 自带工具至今无长截图、无贴图；macOS 自带 Cmd+Shift+3/4/5 + Markup 除了长截图已基本够用。先做 Windows 更容易拿到第一批用户。
  5. 技术选型建议：Tauri 2.0（Rust + 系统 WebView），底层用 xcap 调两端原生采集 API。Electron 与"轻量"诉求直接冲突，Flutter 桌面内存偏高且截图要全自写，Qt 是 Snipaste 验证过的正路但人力成本高。

五、技术选型

5.1 桌面框架对比（截图工具场景）

截图工具的特征是「薄 UI + 重系统调用」——UI 层只负责选区框与标注画布，真正的活儿全在系统原生采集 API 上。

方案 安装包典型值 冷启动内存 调用原生截图 API 生态 已知案例
Tauri 2.0（Rust + 系统 WebView） 3–10MB（实测 exe 4.8MB / dmg 5.2MB） 30–50MB（实测 36MB） 好：xcap crate 已封装 macOS=ScreenCaptureKit、Windows=WGC+GDI tauri-plugin-screenshots、global-shortcut、updater Coco AI 等
Electron 80–150MB（实测 142MB） 118–300MB 弱：desktopCapturer 底层不可控，常需外挂 Swift/C++ helper 最成熟 Kap、eSearch
Flutter Desktop 30–60MB 默认 180–250MB，优化后 ~95MB 差：需 FFI 自己写两端原生 桌面插件稀缺 未查证到截图工具案例
Qt（C++） 较大（Snipaste macOS 包 137MB 含 Qt 全量） 低 最好：C++ 直接调两端 SDK 成熟 Snipaste、Flameshot、xland/ScreenCapture
原生双端（Swift + C#） 最小 最低 最好，新 API 首日可用 — CleanShot X、Shottr、ShareX
Wails（Go） 15–20MB（社区数据，未查证） 50–100MB（未查证） 一般：截图类绑定少 最小 未查证到截图工具类案例

建议：Tauri 2.0。 理由：体积和内存达标（这是"轻量"的硬指标），Rust 侧 xcap / scap 已经把两端采集 API 封装好，UI 用 Web 技术做标注画布开发效率最高。风险是 WebKit（macOS）与 WebView2（Windows）的渲染差异需要双端各调一次。

最高频的坑（务必要在 UI 里显式引导）：授权后必须完全退出（Cmd+Q）再启动才生效，只关窗口无效。 检测用 CGPreflightScreenCaptureAccess()，申请用 CGRequestScreenCaptureAccess()，跳转设置用 x-apple.systempreferences:com.apple.preference.security?Privacy_ScreenCapture。

其他坑： - 三套坐标系并存：NSScreen.frame（左下原点 / points）、kCGWindowBounds（左上原点 / points）、截图缓冲（物理像素）。 - 副屏在主屏左侧时坐标为负。 - Retina：backingScaleFactor 换算。工程上推荐「整屏按原生分辨率抓取 + 内存裁剪」，而不是让 SCK 直接抓选区（社区反馈 captureResolution = .best 仍可能返回逻辑分辨率，未查证 Apple 官方结论）。 - 刘海屏用 NSScreen.safeAreaInsets；多桌面/全屏窗口用 optionOnScreenOnly 过滤。 - 全局快捷键优先用 Carbon RegisterEventHotKey（无需任何权限），NSEvent 全局监听与 CGEventTap 都要辅助功能/输入监控权限。

5.3 Windows 采集方案

方案 最低系统 单窗口 需管理员 DX/游戏画面 说明
Windows.Graphics.Capture（WGC） Win10（社区对 1803/1903 说法不一，运行时用 GraphicsCaptureSession.IsSupported() 判断） ✅ ✗ ✅ 官方推荐。可抓被遮挡/最小化窗口，系统画黄框。HDR 屏需全程 DXGI_FORMAT_R16G16B16A16_FLOAT 避免过曝
DXGI Desktop Duplication Win8+ ✗（整屏后裁剪） ✗ ✅ 最佳（OBS 采用） 1080p 约 2–8ms，GetFrameDirtyRects 脏矩形
GDI BitBlt 全版本 ✅ ✗ ✗ 常黑屏/撕裂 20–50ms@1080p，未声明 DPI 感知会模糊/错位
PrintWindow（+PW_RENDERFULLCONTENT） — ✅ 后台窗口 ✗ ✗ 常黑 兜底

工程实践：三级降级 WGC → DXGI → GDI（OBS、WPS 屏幕共享均如此）。

高 DPI（截图错位的 90% 根源）：启动时 SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)（Win10 1703+），运行时 GetDpiForWindow。未声明感知时 SM_CXVIRTUALSCREEN 与 BitBlt 结果都会被虚拟化缩放。做法同样是「全屏按物理像素抓 + 内存裁剪」，绕开 CopyFromScreen 被二次缩放的问题。

窗口/控件智能识别（四层叠加）： 1. UI Automation：ElementFromPoint() 直接拿到鼠标下元素及 BoundingRectangle，对 WPF / WinForms / 浏览器 / Store 应用最准（Chrome 需 --force-renderer-accessibility）； 2. MSAA / AccessibleObjectFromWindow：老框架兜底； 3. Win32 子窗口枚举：WindowFromPoint → ChildWindowFromPointEx（CWP_SKIPINVISIBLE 用来过滤掉自己那层全屏遮罩）→ RealChildWindowFromPoint，再用 DWMWA_EXTENDED_FRAME_BOUNDS 排除窗口阴影； 4. 边缘检测 / 轮廓识别：给 Electron、Qt、Skia、Canvas 自绘 UI 兜底（这类窗口在 Inspect 里根本没有控件树，新版微信 4.x 就是）。

常见坑：多显示器负坐标（SM_XVIRTUALSCREEN）；HDR/10bit 需 FLOAT 管线；捕获 UAC 提权窗口自身需管理员；以管理员运行时 OLE 拖拽失效（UIPI 限制，常规做法是主进程不提权、按需拉起提权子进程）；RegisterHotKey 仅支持「修饰符+单键」且注册后独占该组合。

5.4 附加能力

长截图（两端同思路，无成熟跨平台库）：选区 → 模拟滚轮 → 逐帧抓 → 重叠检测 → 拼接。

loop {
  frame = capture(region)
  dy    = findOverlap(prev, frame)      // SSD 或 Sobel + 归一化互相关
  if dy == 0: break
  scroll(wheel, dy); sleep(settle ≈ 100ms)
  stitch(prev, frame, dy)
}
  • Windows：SendInput 滚轮 + WGC/BitBlt。开源参考：xland/ScreenCapture（Qt，SSD + QtConcurrent 并行匹配）、scrollshot（Rust，Sobel 梯度 + 模板匹配）。
  • macOS：CGEventCreateScrollWheelEvent + SCK 抓帧，或读 AXUIElement 滚动值。成熟的 macOS 长截图开源库：未查证到——这意味着这块要自己写，也意味着它是护城河。

录屏 / GIF：macOS 走 SCK → AVAssetWriter（三个坑：设 movieFragmentInterval 防崩溃丢文件；SCK 节能机制会让静态画面时长算成 1 秒，停止时需补写最后一帧；窗口捕获模式在副屏会丢失右键菜单等子窗口，改用显示器/区域模式）。Windows 走 Desktop Duplication 或 WGC → Media Foundation。GIF 编码可选 Rust gifski（质量最优）或 gif + imagequant。

OCR 选型：

方案 体积增量 中文准确率 建议
Apple Vision（VNRecognizeTextRequest） 0 好 macOS 10.15+ 默认方案
Windows OCR（Windows.Media.Ocr） 0 中–好 Win10+，需系统已装语言包
PaddleOCR（PP-OCRv4 mobile） ~8–17MB 最高（92–97%） 作为"高精度中文"按需下载
Tesseract 5 语言包数十 MB 85–90%，慢 不推荐

建议默认走系统原生 OCR（零体积），把 PaddleOCR 做成可选模型下载——既守住"轻量"，又不牺牲中文场景。

贴图 / 置顶：macOS 用 NSWindow（.borderless + level: .floating + collectionBehavior: [.canJoinAllSpaces, .fullScreenAuxiliary] + ignoresMouseEvents 穿透）；Windows 用 WS_EX_TOOLWINDOW | WS_EX_LAYERED + SetWindowPos(HWND_TOPMOST)。选区交互的统一做法：每个显示器一个全屏透明无边框覆盖层。

打包分发： - macOS：codesign --options runtime --timestamp → xcrun notarytool submit --wait（通常 1–15 分钟）→ xcrun stapler staple；更新用 Sparkle 2（支持 delta）。 - Windows：微软官方口径——EV 证书自 2024 年起不再即时绕过 SmartScreen；可选 Azure Artifact Signing（约 $9.99/月，限部分地区组织）或 OV 证书（$150–300/年）。signtool 务必加 RFC3161 时间戳。更新用 Velopack（Squirrel.Windows 的活跃继任）。

六、MVP 功能建议

6.1 定位建议

一款两端体验完全一致、冷启动 < 300ms、常驻内存 < 60MB 的截图工具，先把"区域截图 + 标注 + 贴图 + 长截图"四件事做到不输任何人。

不要在第一版做录屏、不要做图床、不要做账号系统。这三样是体积、复杂度和合规风险的主要来源。

6.2 功能优先级

P0 —— 生死线（做不到就别发布）

全屏 / 多显示器截图 正确处理负坐标与混合 DPI 高频 bug 源，早测

功能 说明
长截图（滚动截屏） 全行业最不稳，做稳就是招牌。含手动兜底模式（自动滚动失败时允许手动滚）
本地 OCR 默认系统原生（零体积），可选下载 PaddleOCR 模型
取色器 HEX / RGB / HSL / OKLCH，含 APCA 对比度（对标 Shottr）
截图历史 本地时间线，支持回放与搜索
免安装便携版 Windows 企业环境刚需
截图后动作 复制到剪贴板 / 保存 / 打开编辑器，可配置（先不做上传）

P2 —— 后置（验证需求后再做）

  • 屏幕录制 / GIF（体积与复杂度都高，Mac 端 SCK 坑多）
  • 图床上传（默认关闭，且必须能一键彻底禁用——参考 LightShot 事故）
  • 水印 / 带壳美化 / Backdrop
  • 自动打码敏感信息（邮箱 / 卡号 / token 正则识别）
  • 快捷键工作流 / 插件系统

6.3 差异化三板斧

  1. 不挑 App 的长截图 —— 自动滚动 + 手动兜底 + 失败可回退为「手动拼接」，并把"拼接失败"做成可见的提示而非静默产出错图。
  2. 可量化、可公开的性能承诺 —— 在官网明写包体、冷启动、常驻内存三个数字，并持续公开。在"Electron 全家桶"横行的品类里，这是最有说服力的营销。
  3. 默认本地、默认无账号 —— 不联网也能用全部核心功能，OCR 在本地跑，图床（若做）默认关闭。这是对抗 PixPin（注册要手机号）最直接的一刀。

商业模式建议：一次买断（参考 Shottr $12 / iShot Pro ¥78 / Snipaste ¥45），避免订阅制——iShot 2022 转订阅引发的流失是前车之鉴。

八、下一步

  1. 技术预研（1–2 周）：用 Tauri 2.0 + xcap 出一个最小 demo —— 全局快捷键唤起 → 全屏覆盖层 → 框选 → 保存 PNG。目标是验证双端包体/启动/内存三项指标能否达标。
